# MISS 项目严格验收方法论

本 Skill 规范 MISS 项目的验收报告编写标准，确保每一位验收人产出的报告质量一致、可追溯、可复现。

---

## 一、核心理念

> **不假设，只验证。不臆想，只测量。**

验收的本质不是"看起来差不多就行"，而是**逐项对照设计文档/需求清单，用数据说话**。每一条 PASS/FAIL 必须有对应的代码证据或运行结果支撑。

---

## 二、验收报告标准结构

每份验收报告必须包含以下章节（顺序固定）：

```
1. 报告头 — 任务编号、名称、Phase、日期、结论、验收人
2. 验收标准 — 引用设计文档/任务清单原文
3. 详细验收结果 — 逐项对照（表格化）
4. 测试统计 — 总数/通过/失败/通过率
5. 代码质量评价 — 亮点 + 注意事项
6. 问题与改进建议 — 严重度分类 + 修复方案
7. 既有测试评价（如适用）
8. Spec 对照审计（新增 — 见第十四章）
9. 验收结论 — 综合评分 + PASS/FAIL
10. 附录 — 报告生成时间、验收人、脚本路径
```

---

## 三、报告头部规范

每份报告开头必须包含元信息表格：

```markdown
| 项目 | 内容 |
|------|------|
| **任务编号** | Task X.X / Spec: xxx |
| **任务名称** | 具体名称 |
| **所属Phase** | Phase X：阶段名称 |
| **验收日期** | YYYY-MM-DD |
| **pytest 基准** | N/N |
| **验收结论** | ✅ PASS / ❌ FAIL |
| **验收人** | 严格验收Agent |
```

## 四、验收标准章节

从设计文档/任务拆分清单中**原文引用**验收标准，不可凭记忆描述：

```markdown
## 一、验收标准

> 来源：[任务拆分_代码实现清单.md](file:///...) - Task X.X

### 1.1 核心目标
（引用原文）

### 1.2 验收标准
> （引用原文中的标准语句）

### 1.3 核心数据结构要求（如适用）
（引用原文中的代码/接口定义）
```

对于有 `spec.md` 的 Spec 类验收，必须逐条引用 spec 中的 **ADDED Requirements** 和 **Scenario**：

```markdown
### 1.4 Spec 场景验证（新增格式）

> 来源：[spec.md](file:///...) — Scenario 章节

| Requirement | Scenario | 验证结果 |
|------------|----------|----------|
| 三级 fallback | WHILE 使用中转站 API → LLM 回落 Level 2 | ✅ |
| 属性面板跟随角色 | WHEN 点击"傲娇女友" → THEN 滑块更新 | ✅ |
```

## 五、详细验收结果 — 逐项对照法

这是报告的核心部分。每一项验收点必须用**表格**呈现，包含以下列：

| 序号 | 验收项 | 设计要求 | 实际实现 | 证据 | 状态 |
|------|--------|----------|----------|------|------|

**必须有证据列**：指向具体文件行号（使用 `file:///` 绝对路径 + `#L行号`），或运行结果截图描述。

示例：
```markdown
| 1 | `rational_emotional` 字段 | int, -100~+100, 默认0 | int, ge=-100, le=100, default=0 | [attribute_engine.py#L5](file:///...) | ✅ |
```

常见的逐项对照维度：
- **字段完整性检查**（字段名/类型/默认值/约束）
- **边界值验证**（正向边界 +100、负向边界 -100）
- **超界验证**（+101、-101 必须抛异常）
- **特殊逻辑验证**（如 intimacy 单向范围、easter egg 触发条件）
- **序列化/反序列化**（model_dump → model_validate 一致性）
- **Scenario 端到端**（spec 中的 Gherkin 场景逐条执行）

## 六、测试统计章节

每个子类别单独统计，最后汇总：

```markdown
## 四、测试统计

| 指标 | 数值 |
|------|------|
| 字段完整性 | 11/11 |
| 默认值验证 | 11/11 |
| 边界值验证 | 19/19 |
| 超界验证 | 20/20 |
| 特殊逻辑 | 2/2 |
| **总计** | **77/77（100%）** |
```

项目级验收还需要包含 pytest 全量结果：
```markdown
| 测试文件 | 用例数 | 通过 | 状态 |
|----------|--------|------|------|
| test_profile.py | 43 | 43 | ✅ |
| ... | ... | ... | ... |
| **合计** | **208** | **208** | ✅ |
```

## 七、问题严重度分级

验收中发现的每个问题必须标注严重度，使用统一的四级体系：

| 等级 | 图标 | 含义 | 处理要求 |
|------|------|------|----------|
| **严重** | 🔴 | 阻塞功能 / 导致验收不通过 / 安全漏洞 | **立即修复，修复前不可发布** |
| **中等** | 🟠 | 功能可用但有缺陷 / 未来必然导致线上事故 | 近期修复（下一个迭代） |
| **轻微** | 🟡 | 代码质量 / 最佳实践 / 模块导出不一致 | 择机优化 |
| **建议** | 🔵 | 增强性改进 / 非必需 / 可选优化 | 参考即可 |

## 八、问题记录模板

每个问题必须包含以下字段：

```markdown
### 🔴 问题 ID：简短标题

| 项目 | 内容 |
|------|------|
| **严重程度** | 🔴/🟠/🟡/🔵 |
| **问题类型** | 功能缺失 / 异常处理 / 代码质量 / 安全 / 测试覆盖 / 配置管理 / 线程安全 / ... |
| **状态** | ⏳ 待修复 / ✅ 已修复（日期） |
| **所在文件** | [文件名](file:///绝对路径#L行号) |
| **影响范围** | 受影响的模块/端点/用户场景 |

**问题描述**：
（清晰的文字描述，避免模糊措辞）

**复现步骤**（必须提供）：
```python
# 可执行的复现代码
```

**根因分析**：
（为什么会出现这个问题？为什么现有测试没发现？）

**修复方案**：
```diff
- 旧代码
+ 新代码
```

**修复验证**：
- 方法：pytest / 验收脚本 / 手动验证
- 结果：X/X 通过
```

## 九、修复验证规范

当问题被修复后，在汇总报告中必须追踪修复状态：

**汇总表格式**：
```markdown
| # | ID | 严重度 | 简述 | 状态 | 修复日期 |
|---|-----|--------|------|------|----------|
| 1 | SEC-001 | 🔴 高 | console=True泄露 | ✅ 已修复 | 2026-06-26 |
| 2 | R-2 | 🟡 轻微 | config.py冗余 | ⏳ 待修复 | — |
```

**修复验证必须包含**：
1. 修复前的具体代码行
2. 修复后的具体代码行（diff 形式）
3. pytest 全量回归结果（确保修复未引入新问题）
4. 若无 pytest，则需描述手动验证步骤和结果

## 十、代码质量评价指南

验收不仅要"过"和"不过"，还要评价代码质量。从以下维度给出评分（⭐1-5）：

| 维度 | 评价项 |
|------|--------|
| 模块分层 | models/routers/services 是否清晰分离 |
| 职责分离 | 是否单一职责，有无上帝类 |
| 导出规范 | `__init__.py` 是否导出所有公开类 |
| 配置管理 | 是否使用最佳实践（如 BaseSettings） |
| 数据库 | 是否正确使用 ORM、有无 rollback 保护 |
| 异常处理 | 关键路径是否有 try/except + 降级 + 日志 |
| 类型安全 | 是否使用 TypedDict / type hints |
| 测试覆盖 | pytest 用例数、边界覆盖是否全面 |
| **线程安全（新增）** | UI 线程 IO 是否使用 `Task.Run` 隔离 |
| **API 兼容性（新增）** | LLM 调用是否有三级 fallback |

**亮点**和**需改进**分开陈述，每条必须带有代码行号引用。

## 十一、验收结论章节

必须包含综合评分表和最终结论：

```markdown
| 验收维度 | 权重 | 通过率 |
|----------|------|--------|
| 字段完整性与命名 | 25% | 100% |
| 边界值验证 | 25% | 100% |
| 超界拦截 | 25% | 100% |
| ... | ... | ... |
| **综合** | **100%** | **100%** |

# 🎯 最终结论：Task X.X PASS / FAIL

（一句话结论 + 是否可以进入下一任务/Phase）
```

## 十二、终验报告额外要求

终验（Final Acceptance）报告需增加：

1. **文件清单表**（所有核心文件：文件名、类/函数、行数）
2. **运行时验收**（API 端点 HTTP 状态码验证表）
3. **各 Task 汇总表**（Task编号、名称、结论、关键成果）
4. **问题全景图**（全项目问题统计：总数/严重/中等/轻微/建议/已修复/待修复）
5. **架构评价表**（各维度星级评分）
6. **ASCII 终验结论框**（可视化总结）

## 十三、文件路径引用规范

在验收报告中引用代码位置时，必须使用 `file:///` 绝对路径格式：

```markdown
[services/attribute_engine.py](file:///d:/Desktop/MISS/miss-backend/services/attribute_engine.py#L4-L16)
```

- 必须带行号（`#L起始-结束` 或 `#L行号`）
- 路径必须为绝对路径
- 后续查看报告的人可 Ctrl+Click 直接跳转

## 十四（新增）：Spec 对照审计

如果验收对象是执行 `spec.md` 的 Spec 类任务（如 `fix-binding-and-api`），必须在验收报告中新增 **Spec 对照审计** 章节，逐条检查：

### 14.1 What Changes 完成度

从 spec 的 `## What Changes` 框逐条迁移到验收表：

| # | Spec 要求 | 实现证据 | 代码行 | 状态 |
|---|-----------|---------|--------|------|
| 1 | 推理模型检测 → Mode.JSON | `_is_reasoning_model()` 已实现 | llm_caller.py L34-38 | ✅ |
| 2 | 属性面板跟随角色切换 | `OnCurrentRoleChanged` 同步 10 维属性 | MainViewModel.cs | ✅ |
| 3 | 对话视图角色感知 | 标题栏 `CurrentRole.Name` 绑定 | ConversationView.xaml | ✅ |

### 14.2 Scenario 验证（端到端）

每一条 Scenario 必须亲自触发验证：

```markdown
| Scenario | 触发条件 | 预期结果 | 实际结果 | 截图/日志 |
|----------|---------|----------|----------|----------|
| 推理模型正常对话 | 选 deepseek-reasoner 发送消息 | 无 400 报错 | ✅ 正常回复 | log: "level=1" |
| 属性面板跟随切换 | 点击"傲娇女友" | 滑块从 0 变为该角色值 | ✅ 全部更新 | screenshot |
```

### 14.3 代码 diff 验证（spec 要求的修改范围）

spec 的 `## Impact` 中说改了哪些文件，验收时必须逐文件确认：

```markdown
| 文件 | Spec 预期修改 | 实际 diff | 多余修改 | 遗漏 |
|------|-------------|-----------|---------|------|
| llm_caller.py | +50/-40 行 | +48/-42 | 0 | 0 |
| routers/settings.py | +25 行 | +27 | 0 | 0 |
| test_llm_json_parse.py | +10 行 | +15 | +5（额外 case） | 0 |
```

## 十五（新增）：退回归档与回归验证

### 15.1 回归测试链

验收通过后，验收人必须验证**全量回归**：

```bash
pytest tests/ -v --tb=short
```

**预期**：当前基准 **208/208**。任何下降必须写入问题。

### 15.2 验收脚本回归

```bash
# 运行所有验收脚本
cd miss-backend
python -m pytest tests/acceptance_*.py -v --tb=short
```

### 15.3 旧 PASS 结论不受影响声明

修复引入的新问题不能推翻已有的 PASS 结论。验收人必须在报告中明确声明：

```markdown
**先前验收结论是否受影响**

| Task | 先前PASS | 受影响 | 说明 |
|------|----------|--------|------|
| 0.1-1.4 | ✅ PASS | 不受影响 | Phase 1 组件无数据库依赖 |
| 2.1 | ✅ PASS | 不受影响 | Jinja2 模板无运行时依赖 |
```

## 十六（新增）：置信度审计（Confidence Audit）

当一个 Spec 涉及**重大架构变更**或**高风险重构**时，管线工程师应产出 `confidence-audit.md` 配套文档（如 `fix-llm-api-compat/ confidence-audit.md`）。

验收人必须阅读并审计以下内容：

| 审计维度 | 验收标准 |
|---------|----------|
| **整体可行性** | 审计给出了明确的百分比等级（≥85% 视为高置信度） |
| **最大风险** | 识别的风险点已被代码封堵（如"原文当 spoken"已添加安全占位符） |
| **架构冗余** | 验收人确认简化方案是否更优 |
| **工作量估算** | 代码行数估算与实际 diff 偏差 ≤30% |
| **剩余工作清单** | 每条工作有编号、文件路径、行数估算 |

---

## 十七、核心检查清单

每次验收前，验收人必须自检以下项：

- [ ] 报告头完整（任务编号/日期/结论/验收人 + pytest 基准）
- [ ] 验收标准原文引用自设计文档（含链接）
- [ ] 每一项验收点有表格对照（含证据列）
- [ ] 测试统计数据准确
- [ ] 发现的问题有严重度标记
- [ ] 每个问题有复现步骤 + 修复方案
- [ ] 代码质量评价有亮点 + 需改进
- [ ] Spec 对照审计完成（What Changes + Scenario + Impact diff）
- [ ] pytest 全量回归 208/208 确认
- [ ] 旧 PASS 结论是否受影响声明
- [ ] 验收结论明确（PASS 或 FAIL）
- [ ] 所有文件引用使用 file:/// 绝对路径 + 行号
- [ ] 报告末尾包含生成时间和验收人签名
