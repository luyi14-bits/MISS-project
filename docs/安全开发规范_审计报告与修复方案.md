## 三、逐项修复方案

### S01 — 全 API 无认证/授权

**文件**：`miss-backend/main.py`、所有 `routers/*.py`

**问题**：所有端点无需任何认证即可访问。`POST /api/settings` 无保护；`DELETE /api/preset/{id}` 可被任意调用。

**修复方案**：引入 Bearer Token 认证中间件，不设 `ACCESS_TOKEN` 时不校验。

**代码示例**：

```python
# miss-backend/middleware/auth.py
PUBLIC_PATHS = {"/health", "/api/info", "/docs", "/redoc", "/openapi.json"}

class AuthMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request: Request, call_next):
        token = config.access_token
        if not token or request.url.path in PUBLIC_PATHS:
            return await call_next(request)
        auth = request.headers.get("Authorization", "")
        if not auth.startswith("Bearer ") or auth[7:] != token:
            raise HTTPException(status_code=401, detail="未授权访问")
        return await call_next(request)
```

### 应用层审计

#### 发现 1：SSE error token 的硬编码 JSON 字符串拼接

**位置**：`PythonBridge.cs:L106-L108`

```csharp
// 修复前
tokens.Add("data: {\"_error\":true,\"message\":\"后端流处理失败\"}\n\n");
```

**PoC**: 如果错误消息包含 `"` 或 `\n`，字符串拼接产生非法 JSON → C# 侧 `MainViewModel.cs` L363 `JsonSerializer.Deserialize` 静默失败 → 整个流式响应丢弃 → 用户看不到错误提示。

**CVSS 3.1**: 4.3 (Medium) — AV:L/AC:L/PR:N/UI:N/S:U/C:N/I:L/A:N

**修复**: 改用 `System.Text.Json.JsonSerializer.Serialize()` 动态序列化 → ✅ 已完成。

#### 发现 2：ChatStream GIL 持有策略评估

`PythonBridge.cs` 的 `ChatStream()` 中 Python generator 的 `foreach` 消费在 dedicated worker thread 内执行。pythonnet 的 `foreach` 在 `MoveNext()` 时通过 `Py.GIL()` 进入 Python 获取下一个 token。

**评估**：这不是 bug——`PythonBridge.StartWorker()` L19-L37 创建了专用 `STA` 后台线程，所有 Python 操作在此单一线程内串行化执行。这恰是 pythonnet 的最佳 GIL 模式（单线程序列化），从根本上消除了死锁风险。

**代价**：流式对话期间，其他 Python 操作（`ApplySettings` / `GetSettings`）需排队等待——但因为 `_workQueue` 是 `BlockingCollection<Action>`，不会死锁。

**Web 安全评价**：A。单线程序列化是 pythonnet 的最佳实践，不需改动。

#### Web 安全评分：A

#### 发现 1：DLL 搜索路径污染风险

**位置**：`PythonEngineService.cs:L34`

```csharp
AddDllDirectory(pythonHome);  // pythonHome 可能来自 C:\Program Files\Python312
```

`AddDllDirectory` 将 Python 目录加入 Windows DLL 搜索链。若该目录的 ACL 为 Users:Write（标准 Python 安装默认），攻击者可放置恶意 `python312.dll` 或 `vcruntime140.dll`。

**CVSS 3.1**: 3.9 (Low) — AV:L/AC:H/PR:H/UI:N/S:U/C:L/I:L/A:L

攻击前提：已具备文件系统写权限 → 有权限 → 优先级降低。`Release` 编译时优先使用嵌入 `python/` 目录（不存在时才走到系统路径），进一步缩小风险窗口。

**当前防护**：`PythonEngineService.FindPythonHome()` L112-L128 优先搜索嵌入 `python/` 目录，系统路径只在最后 fallback。✅

#### 发现 2：`init(data_dir)` 无路径穿越校验

**位置**：`desktop_bridge.py:L41`

```python
os.makedirs(data_dir, exist_ok=True)
```

**Fuzzer 设计**：

```python
def fuzz_data_dir():
    payloads = [
        "../../Windows/System32",
        "\\\\?\\C:\\Windows",
        "A" * 260,
        "%TEMP%/../../Windows",
    ]
    for p in payloads:
        # 验证：不应在不合法的路径上成功执行
        result = desktop_bridge.init(p)
        assert "ok" in result or "PermissionError" in str(result)
```

**当前防护**：`data_dir` 来自 `App.xaml.cs:L19` 的 `Environment.GetFolderPath(ApplicationData)` — Windows 证书路径，不可篡改。

**二进制安全评价**：C# 侧的路径源是可信的，Python 侧不需要额外校验。但如果有第三方 WPF 插件系统或扩展点可以绕过 `App.xaml.cs` 直接调 `init()`，则需警惕。

#### 发现 3：`crypto.Fernet.generate_key()` 随机性审计

```python
_cipher = Fernet(Fernet.generate_key())  # 无 MISS_FERNET_KEY 时
```

`Fernet.generate_key()` 内部使用 `os.urandom(32)` — 加密级随机性 ✅。Python 3.12 的 `os.urandom()` 在 Windows 上调用 `BCryptGenRandom` — 与 Windows CryptoAPI 同源 ✅。

**结论**：密钥随机性无问题。但每次启动新密钥意味着旧密文不可读 → 需部署文档明确标注：生产环境必须设置 `MISS_FERNET_KEY` 环境变量。

#### 二进制安全评分：A-

DLL 路径风险已通过嵌入 `python/` 优先级缓解。唯一建议：在 `pythonengineservice.cs` 中加注释标注 DLL 搜索链的安全假设。

## 四、安全开发规范

### 4.1 API 设计原则

| 原则 | 说明 |
|------|------|
| 最小权限 | 每个端点仅开放完成任务所需的最小能力和数据 |
| 默认拒绝 | 未明确允许的访问应该被拒绝 |
| 白名单优先 | 使用白名单而非黑名单进行过滤 |
| 纵深防御 | 多层防护，单点失效不影响整体安全 |

### 4.2 数据保护规范

```
机密数据流转约束：
  ┌──────────┐    加密传输     ┌──────────┐    仅内存持有    ┌──────────┐
  │ 前端 UI  │ ◄─────────────► │  后端    │ ◄─────────────► │ LLM API │
  │          │   不落盘/不     │          │   不落日志        │          │
  │          │   写入 localStorage │    │                   │          │
  └──────────┘                  └──────────┘                   └──────────┘

禁止：
  ✗ API Key 写入 localStorage / IndexedDB
  ✗ API Key 打印到控制台日志
  ✗ API Key 出现在 URL query string 中
  ✗ 数据库密码硬编码在代码中
```

### 4.3 输入输出规范

- **所有外部输入必须校验**：长度、类型、范围、格式
- **所有输出必须脱敏**：异常堆栈、数据库错误、内部路径不返回给客户端
- **日志分级**：`DEBUG`（开发）/ `INFO`（正常）/ `WARNING`（异常但不致命）/ `ERROR`（需告警）

### 4.4 依赖安全

```bash
# 定期执行
pip list --outdated          # 检查过时依赖
pip-audit                    # 检查已知漏洞（需安装 pip-audit）
npm audit                    # 前端依赖审计
```

### 4.5 版本控制安全

- `.env` **必须**在 `.gitignore` 中（当前已配置 ✓）
- `*.db`、`*.sqlite3` **必须**忽略（当前已配置 ✓）
- 确认没有其他文件意外提交了密钥（使用 `git log -p --all | grep -i "api.key\|password\|secret"`）
