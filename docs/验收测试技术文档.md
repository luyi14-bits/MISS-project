## 一、测试哲学

### 1.1 核心理念

> **不假设，只验证。不臆想，只测量。**

MISS 项目的验收测试体系以 **TDD 铁三角**（Kent Beck 单元测试方法论 + Brian Okken pytest 架构 + Simon Stewart E2E 稳定性方法论）为基础，结合本项目的 `coding-ethics`（编程八荣八耻）行为准则，形成了**三层覆盖 + 逐项对照 + 严重度分级 + 修复追踪**的闭环验收标准。

### 1.2 验收人准则

验收人不写代码，只做三件事：

1. **逐文件读回** — 独立打开修复工程师声称修改的文件，逐行对照修复声明
2. **实测执行** — `dotnet build` / `dotnet publish` / `pytest` / 手动启动，验证运行时行为
3. **证据可视化** — 每一项 PASS/FAIL 必须带有 `file:///` 绝对路径 + 行号引用，可 Ctrl+Click 跳转

验收人和修复工程师是**对立角色**：修复工程师说"修好了"，验收人的默认假设是"没修好，直到证据说服我"。

### 1.3 铁律：永远不信任修复工程师的声明

修复组提交的报告中声称"FULL PASS"、 "全部通过"、 "零遗留"——验收人必须以最坏情况心态独立验证：

| 修复组声明 | 验收人动作 |
|-----------|-----------|
| "pytest 189/189" | 自己跑 `pytest -q` |
| "dotnet build 0 error" | 自己跑 `dotnet build -c Release` |
| "ContentRendered → 正常启动" | 自己 `dotnet publish` → 双击 `MISS.exe` → 计时 |
| "LiteDbLocalStore 加密了" | 自己读 `SaveSettings` 函数 |

MISS 项目历史上发生过多次"修复组报告 PASS 但验收人实测发现未修"的情况——这恰好证明了独立验收的必要性。

## 三、验收报告标准结构

每份验收报告遵循固定的 10 段式结构，确保所有验收人的产出质量一致。

### 3.1 报告头部

```markdown
| 项目 | 内容 |
|------|------|
| **任务编号** | Task X.X / Spec: xxx |
| **任务名称** | 具体名称 |
| **所属Phase** | Phase X：阶段名称 |
| **验收日期** | YYYY-MM-DD |
| **pytest 基准** | N/N |
| **验收结论** | ✅ PASS / ❌ FAIL |
| **验收人** | 严格验收Agent + 三位导师签名 |
```

### 3.2 10 段标准结构

```
1. 报告头 — 任务编号 / Phase / 日期 / pytest 基准 / 验收人
2. 验收标准 — 引用 spec.md 或设计文档原文
3. 详细验收结果 — 逐项表格对照（含 file:/// 证据）
4. 测试统计 — 子项汇总
5. 代码质量评价 — 亮点 + 注意事项
6. 问题与改进建议 — 严重度分类 + 修复方案
7. 既有测试评价
8. Spec 对照审计（如有）
9. 验收结论 — 综合评分 + PASS/FAIL
10. 附录 — 生成时间 / 验收人 / 脚本路径
```

### 3.3 逐项对照表格式

```markdown
| 序号 | 验收项 | 设计要求 | 实际实现 | 证据 | 状态 |
|------|--------|----------|----------|------|------|
```

## 四、问题严重度四级体系

MISS 项目使用统一的四级严重度标记，所有发现问题必须归属以下之一：

| 等级 | 图标 | 含义 | 处理要求 | 本项目中出现次数 |
|------|------|------|----------|-----------------|
| **严重** | 🔴 | 阻塞功能 / 验收不通过 / 安全漏洞 / 双击即崩 | **立即修复，修复前不可发布** | 4 |
| **中等** | 🟠 | 功能可用但有缺陷 / 未来必然导致线上事故 | 近期修复（下一个迭代） | 10+ |
| **轻微** | 🟡 | 代码质量 / 最佳实践 / 导出不一致 | 择机优化 | 8+ |
| **建议** | 🔵 | 增强性改进 / 非必需 / 可选优化 | 参考即可 | 8+ |

### 4.1 🔴 严重问题的典型模式

| 模式 | MISS 实例 |
|------|----------|
| 资源路径在 publish 中找不到 | CRASH-003: `Source="/Resources/..."` 在 self-contained 中抛 IOException |
| 启动事件在 publish 中不触发 | CRASH-001: `ContentRendered` / `BeginInvoke` / `Post` 在 NativeAOT trim 下永不到达 |
| API 密钥明文落盘 | SEC-003: `SaveSettings` 将 `openai_api_key` 完整序列化到 JSON 文件 |
| 日志系统在 publish 中静默 | SEC-002: `logging.basicConfig` 在 `if __name__=="__main__"` 内 → publish 模式不执行 |

### 4.2 问题记录模板

```markdown

| 项目 | 内容 |
|------|------|
| **严重程度** | 🔴 |

| **状态** | ⏳ 待修复 / ✅ 已修复（日期） |
| **所在文件** | [文件名](file:///绝对路径#L行号) |
```

## 七、Spec 驱动验收流程

### 7.1 Spec 结构

```
.trae/specs/{spec-name}/
├── spec.md              # What Changes / Impact / Requirements / Scenario
├── tasks.md             # Task 拆分 + 依赖 + 技术要点
├── checklist.md          # 逐项检查清单
└── confidence-audit.md  # 置信度审计（高风险 Spec 必选）
```

### 7.2 Spec 对照审计（验收报告核心章节）

每份针对 Spec 的验收报告必须包含：

| 章节 | 内容 |
|------|------|
| **What Changes 完成度** | 逐条迁移 spec 要求到验收表，标注实现证据 + 代码行 |
| **Scenario 验证** | Gherkin 场景逐条触发验证 |
| **Impact diff** | 逐文件确认修改范围与 spec 声明一致 |

### 7.3 偏离 spec 的处理

如果修复方案与 spec 不同但更优（如角色隔离的 Filter 方案比 spec 的 DeleteMany+Insert 更干净），验收人必须：

1. 明确标注 "偏离 spec，更优" 
2. 写出 spec 方案 vs 实际方案对照
3. 确认无副作用

## 十、常见验收陷阱与教训

### 10.1 陷阱 1：相信修复组的 BUILD/PASS 声明

**教训**: 修复组提交了 4 轮报告，每轮声称 "FULL PASS / 全部通过"。验收人独立测试后发现：

- 第 3 轮: `LiteDbLocalStore.cs` 编译错误（`Dictionary<>` 无 `.openai_api_key`）
- 第 3 轮: `character.py` 绕过 LLMCaller 封装层
- 第 4 轮: `async void + await` 实测 publish 40s timeout

**规则**: **永远自己跑 build / pytest / publish 启动**。

### 10.2 陷阱 2：仅在 dev 环境测试

**教训**: `ContentRendered` / `BeginInvoke` / `SynchronizationContext.Post` 在 Visual Studio 调试/直接运行中正常工作，但在 `dotnet publish --self-contained` 后的 `MISS.exe` 中全部不触发。

**规则**: **验收必须使用 `dotnet publish` 产物，而非 bin/Debug 目录**。

### 10.3 陷阱 3：XAML 中的 Resource 路径

**教训**: `Source="/Resources/Images/p-tsundere.jpg"` 在 dev 环境正常（编译期嵌入），但在 self-contained publish 中抛 IOException。

**规则**: **所有图片资源引用必须使用文件系统路径（`Path.Combine(BaseDir, ...)` + `File.Exists()`）**。

### 10.4 陷阱 4："Python 侧零改动" 不等于零影响

**教训**: 角色隔离方案中 `pySessionId` 在 C# 侧拼接 `sess_{Id}_{roleName}`，Python 侧 code 零改动。但 Python SQLite 中同一 session 的历史消息会因 session_id 不同而物理隔离——这是正确的行为，但需要验收人理解 Python 侧代码来验证。

**规则**: **"零改动" 不等于 "零影响"。验收人必须理解 Python 侧的逻辑，而不只看 diff**。

## 附录 B：Coding-Ethics 快速自检表

提交代码前逐项自问（来自 MISS 项目 40 个验收问题的教训）：

1. 新增了公开类/函数？ → 去 `__init__.py` 加导出了吗？
2. 写了数据库操作？ → 有 `rollback` 和 `finally: close()` 吗？
3. 写了新模块？ → 有对应的 `tests/test_xxx.py` 吗？
4. 改了现有 API？ → 旧测试同步更新了吗？
5. 调了第三方 SDK？ → 走的是项目封装层还是原生调用？
6. 用了数据库专有参数？ → 有多数据库适配吗？
7. 返回值是 dict？ → 定义 TypedDict 了吗？
8. Pydantic Field？ → 加了 `description` 吗？
9. 有副作用操作？ → 在 `lifespan` 里还是模块级？
10. 涉及密钥/会话？ → 有没有硬编码、console 打印、明文落盘？
